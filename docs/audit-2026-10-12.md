# AeroOpt implementation audit — 2026-10-12

## Verified architecture

- Frontend: React 19, TypeScript, Vite, Lucide icons; single-page application in `frontend/src/App.tsx`, shared HTTP helper in `frontend/src/api.ts`.
- Backend: FastAPI app and routes in `backend/app/main.py`, Pydantic request models, SQLAlchemy ORM models, SQLite default via `backend/app/db.py`.
- Persistence: `aircraft`, `personnel`, `tasks`, `assignments`, `solver_runs`, `audit_events`; SQLAlchemy metadata is registered in `backend/app/models.py`.
- Optimization: deterministic greedy baseline and optional OR-Tools CP-SAT in `backend/app/optimization/engine.py`; independent validator and canonical input hash.
- Audit: SHA-256 hash chain in `backend/app/services/audit.py`.

## Prioritized findings

### P0 — Correctness / data integrity

1. **Resource limits were checked per task but not cumulatively.** `eligibility_reasons` compares historical usage plus one task against the maximum. The independent validator now also totals all assignments on each aircraft/crew member and rejects cumulative overuse; the greedy baseline checks accumulated scheduled durations before accepting a candidate.
2. **Greedy dependency ordering depended on priority sort.** A high-priority task could be visited before its lower-priority prerequisite and incorrectly reported unassigned. The baseline now selects the highest-priority task among those whose dependencies are already scheduled or completed.
3. **Validator turnaround/rest checks depended on input order.** The validator now sorts each resource's intervals and checks gaps symmetrically, regardless of the order assignments arrive in.
4. **Solve request accepted arbitrary solver strings.** It now restricts the solver to `greedy` or `cp-sat` and bounds time limit/stability weight.
5. **Update endpoints accepted mismatched path/body IDs.** Aircraft, personnel, and task update endpoints now reject mismatches with HTTP 422.
6. **Alembic ignored `DATABASE_URL` online.** `migrations/env.py` now uses the same configured SQLAlchemy engine as the application. A fresh SQLite migration was executed and its tables verified.

### P1 — Missing user workflows / incomplete integration

1. Follow-up pass added JSON-based create/edit UI for aircraft, personnel, and tasks, plus archive/cancel actions. Archived-record restore remains API-only; field-by-field forms are not implemented.
2. Scenario Lab is explicitly not implemented; `/api/v1/scenarios` reports `implemented: false` rather than pretending scenarios are isolated.
3. CP-SAT is optional and was not executable in this environment because OR-Tools was not installed. Its constraint model still needs further verification before it can be relied on for all resource and time constraints.
4. Frontend install/build/test could not be verified because npm installation timed out. A Vitest test file was added for API success and failure handling, but not run.

### P2 — Operational hardening

- JSON text fields are not normalized relational structures.
- No auth/roles or concurrency-safe approval/version locking are implemented.
- No live data providers, telemetry streaming, counterfactuals, stress testing, or replay verification are connected.
- Seeded assignments are explicitly hand-authored synthetic fixture data, not solver output or live intelligence.
